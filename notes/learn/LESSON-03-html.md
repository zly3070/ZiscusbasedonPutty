## 3.0 为什么从它入手

这个文件**没有数据库、没有网络、没有 async、没有 env**。它只做一件事：

> **把字符串里的特殊字符换成安全的形式，以及反过来。**

**⭐ 这种"给同样的输入永远得到同样的输出、不碰外部世界"的函数，叫「纯函数」（pure function）。**

**为什么纯函数好读：**

|              | 纯函数（本文件）     | 非纯函数（如 `submit.ts`）        |
| ------------ | -------------------- | --------------------------------- |
| 输入         | 只有参数             | 参数 + 数据库状态 + 网络 + 环境变量 |
| 输出         | 只有返回值           | 返回值 + **副作用**（写库、发请求） |
| 能不能预测   | ✅ 心里就能算出来     | ❌ 要看运行时状态                  |
| 好不好测     | ✅ 极易（无需 mock）  | 要准备数据库、mock 服务            |

**⭐ 读代码的正确顺序是"从纯到杂"。** 这也是人家把这一课安排在这里的原因。

## 3.1 唯一的新语法：正则表达式 `regex`

**先看文件里最有代表性的一行：**

```ts
.replace(/&/g, "&amp;")
//       ↑       ↑
//    找什么    换成什么
```

**`.replace(A, B)` 就是"把 A 换成 B"。** 而 `A` 有两种写法：

```ts
"abc".replace("a", "x")       // 普通字符串：只换【第一个】 "a"
"abc".replace(/a/g, "x")      // 正则 + g：换【所有】 "a"
//            ↑  ↑
//        斜杠包围   g = global（全部）
```

**⭐ 那个 `/.../ ` 的写法就是正则表达式（regex）。** 你项目里到处是它。

### 这一课只需要认识这几个符号

| 符号        | 意思                               | 大白话                       |
| ----------- | ---------------------------------- | ---------------------------- |
| `/.../ `    | 正则的字面量写法                   | "我要用一个模式去找东西"     |
| `/.../g`    | 结尾的 `g` = **global**            | **全都找**（不加 g 只找第一个） |
| `\0`        | NUL 空字节                         | 一个不可见的控制字符         |
| `[abc]`     | 字符组                             | "a、b、c 里任意一个"         |
| `\u200B`    | Unicode 码点写法                   | 一个"零宽空格"，肉眼看不见   |
| `.`         | **任意一个字符**（⚠ 不是句号！）   |                              |
| `\1`        | **反向引用**：和前面第 1 个括号匹配到的内容相同 |                  |
| `{19,}`     | 重复 **19 次或更多**               |                              |
| `\.`        | 转义后的句号，**真的找一个点**     |                              |

**用一个例子串起来**（这个正则在 `structural-filter.ts` 里能见到）：

```ts
/(.)\1{19,}/
// ↑↑ ↑↑
// │└─ 重复 19 次以上
// └── 一个括号：捕获"任意一个字符"
//
// 整体意思：同一个字符连续出现 20 次以上
// "aaaaaaaaaaaaaaaaaaaa"  → 匹配 ✅
// "哈哈哈"                → 不匹配（只有 3 个）
```

**⭐ 记住读法：正则就是"用符号描述一个模式"。不认识的符号就查，不用背。**

### ⚠️ 正则的一个坑（你以后一定会踩）

```ts
"a.b".replace(/./g, "X")     // → "XXX"   ⚠ . 在正则里是"任意字符"！
"a.b".replace(/\./g, "X")    // → "aXb"   ✅ 想找句号要写 \.
```

## 3.2 `escHtml`：六个替换，一条链

```ts
export function escHtml(s: string): string {
  return s
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;")
    .replace(/\0/g, "");
}
```

### 逐块拆解函数签名

```ts
export function escHtml(s: string): string {
// ↑      ↑       ↑  ↑        ↑
// ①      ②       ③  ④        ⑤
```

| #   | 代码             | 意思                                                            |
| --- | ---------------- | --------------------------------------------------------------- |
| ①   | `export`         | **导出**，让别的文件能 `import { escHtml }` 用它                 |
| ②   | `function escHtml` | 函数名。**驼峰命名**：`escHtml` = "escape HTML"                |
| ③   | `s`              | 参数名，代表"要转义的字符串"                                     |
| ④   | `: string`       | **类型标注**：`s` 是字符串（运行时会被擦掉 —— 第 2 课学过）      |
| ⑤   | `: string`       | **返回值**也是字符串                                             |

### 核心：`.replace()` 的**链式调用**

**⭐ 这叫「链式调用」（method chaining）。读法是"上一步的输出当作下一步的输入"。**

**用具体字符串走一遍**，输入 `<b>hi</b>`：

```
初始             <b>hi</b>
解 &     之后     <b>hi</b>            （没有 &，没变化）
解 <     之后     &lt;b>hi&lt;/b>      （两个 < 都换了）
解 >     之后     &lt;b&gt;hi&lt;/b&gt;
解 "     之后     同上（没有双引号）
解 '     之后     同上
解 \0    之后     同上
最终结果          &lt;b&gt;hi&lt;/b&gt;
```

**⭐ 这就是"转义"的直观效果：** 尖括号变成 `&lt;` `&gt;`，
浏览器会把它们当**普通文字**显示，而不是当成标签执行。

### 六个替换分别防什么

| 替换            | 防的问题                                                       |
| --------------- | -------------------------------------------------------------- |
| `&` → `&amp;`   | **必须第一个做**（原因见 3.3，这是本课重点）                    |
| `<` → `&lt;`    | 防止 `<script>` 这类标签被执行 → **XSS 的主要入口**             |
| `>` → `&gt;`    | 同上，补齐标签的另一半                                          |
| `"` → `&quot;`  | 防止**属性逃逸**：`<a title="${x}">` 里注入引号就能加新属性     |
| `'` → `&#39;`   | 同上，单引号版本的属性逃逸                                      |
| `\0` → **删除** | NUL 空字节。某些解析器会在这里截断字符串，可被用来绕过检查      |

**⭐ 注意最后一条是"换成空字符串"= 删除。**

## 3.3 ⭐ 本课重点：`unescapeHtml` 里那个"顺序陷阱"

```ts
export function unescapeHtml(s: string): string {
  return s
    .replace(/&lt;/g, "<")
    .replace(/&gt;/g, ">")
    .replace(/&quot;/g, '"')
    .replace(/&#39;/g, "'")
    .replace(/&amp;/g, "&")        // ← ⚠ 这个必须在最后！
}
```

### 为什么 `&amp;` 必须最后？

**先看它要解决什么问题。** 假设评论者**真的想输入** `&lt;` 这四个字符
（打比方，他在讨论 HTML）：

```
他输入的             &lt;
入库时 escHtml 后    &amp;lt;      ← & 被转义成了 &amp;
```

**要显示回他原本打的 `&lt;`，就要解码一次：**

```
要解的目标   &amp;lt;
期望结果     &lt;          （他还想看到这四个字符）
```

**如果 `&amp;` 这一步【先】执行：**

```
& 先解：  &amp;lt;   →   &lt;      ← 变成尖括号实体了
接着 < 的规则命中它：
          &lt;       →   <        ❌ 变成尖括号，用户内容被吃掉一层
```

**如果 `&amp;` 这一步【最后】执行：**

```
解 &lt;  ：  &amp;lt; 里没有 "&lt;" 子串（l 前面是 ; 不是 &）→ 不动
解 &gt;  ：  不动
解 &quot;：  不动
解 &#39;：  不动
解 &amp; ：  现在才解 → &lt;    ✅ 正是他要的
```

**⭐ 注意第 2 步那个细节**：`&amp;lt;` 的字符序列是 `& a m p ; l t ;`，
**里面没有 `&lt;` 这个子串**（`l` 前面是 `;` 不是 `&`），所以前四条规则都碰不到它。
两条规则是**配合关系**，不能单独改其中一条。

### 人家做过验证（真实实验，不是推理）

人家当时也不确定，所以写了个脚本**穷举 5 条规则的【全部 120 种排列】**：

```powershell
node notes/verify-unescape-rule-order.mjs
```

**结果：**

```
输入 "&amp;lt;"
   60 种顺序 → "&lt;"   ✅ 正确（这些顺序里 &amp; 都在 &lt; 之后处理）
   60 种顺序 → "<"      ❌ 错误（这些顺序里 &amp; 提前处理了）
```

**⭐ 结论：顺序【确实重要】，分界线就是"`&amp;` 是否在 `&lt;` 之后"。**

### ⚠️ 还有一个更隐蔽的坑：**只能调用一次**

`unescapeHtml` **不是幂等的** —— 调两次会连续剥掉两层实体：

```
"&amp;amp;"   --第1次-->   "&amp;"   --第2次-->   "&"    ❌ 用户内容被吞掉
```

**所以渲染端必须严格写成：**

```ts
escHtml(unescapeHtml(存的值))
//       ↑ 只能调一次
```

**⭐ 你在 `html-rewriter.ts` 和 `embed/src/render.ts` 里都会看到这个固定搭配，现在你知道为什么了。**

### 完整的数据流

```
用户输入  ──escHtml──→  存入数据库  ──unescapeHtml──→  用户的原文
   ↑                                                          │
   └──────────── 中间必须严格对称（后面的练习会验证这点）─────┘

渲染输出  ──escHtml──→  浏览器显示
           ↑
      这里再转一次，是【兜底防线】：
      即使某行数据绕过了存储规则（没转义就入库），也不会 XSS
```

## 3.5 ⭐ 这里有个"反直觉"的结论，是本课最值钱的地方

**为什么改 `worker/src/html.ts` 不影响任何测试？**

**因为 `escHtml` 在项目里有【两份独立副本】：**

| 位置                     | 谁在用                             | 谁在测                             |
| ------------------------ | ---------------------------------- | ---------------------------------- |
| `worker/src/html.ts`     | Worker 运行时（`html-rewriter.ts`） | **没有专门的测试文件**             |
| `embed/src/render.ts`    | 你的 SSG 构建过程                   | `embed/src/render.test.ts` ✅       |

**⭐ `render.test.ts` 测的是 `embed/src/render.ts` 那一份，不是 worker 的。**

### 为什么会有两份？（第 1 课解释过）

```
worker 包  →  部署到 Cloudflare
embed 包   →  从 npm 装到你的构建环境
两者【不能互相 import】（不同的构建产物、不同的运行环境）
        ↓
代价：同一个工具函数要各写一份
```

**这正是人家在第 1 课说的"跨包契约"的一个具体后果。**
**⚠️ 所以改动前要问自己：这个函数在别处有没有副本？**

## 3.7 往返测试（round-trip test）为什么值钱

**看那条抓出 bug 的测试：**

```ts
const fixtures = [
  "plain text, no entities",
  "Tom & Jerry",
  "<script>alert(1)</script>",
  `He said "hi" and 'bye'`,
  `all five: & < > " '`,
  `bobby tables"`,
  "&lt; typed literally by the author",
  "",
];

it.each(fixtures)("round-trips %j through escHtml", (s) => {
  expect(unescapeHtml(escHtml(s))).toBe(s);      // ← 就这一行
});
```

**⭐ 这一行断言的威力在于它是【属性】，不是【具体值】：**

| 断言方式                     | 表达的意思                       | 改动时会不会抓到 bug     |
| ---------------------------- | -------------------------------- | ------------------------ |
| `expect(escHtml("'")).toBe("&#39;")` | "这个输入必须得到这个输出"  | ❌ 只覆盖你想到的那一种  |
| **`expect(unescapeHtml(escHtml(s))).toBe(s)`** | **"对任意 s，往返必须回到原样"** | ✅ **任何破坏对称的改动都会挂** |

**而且 `it.each(fixtures)` 是"参数化测试"** —— 同一段断言跑好几组数据，
一次写、多组覆盖，比复制粘贴好几遍聪明。

**⭐ 你以后设计自己的函数时可以问：**

> **"我的操作有没有一个可逆的搭档？如果有，写一条往返测试。"**

**适用场景：转义/反转义、编码/解码、序列化/反序列化、压缩/解压、
加密/解密、格式化/解析…… 这类成对操作全都适用。**

## 3.8 正确的改法（四个地方 + 一条断言）

**要真正完成这个改动，需要动：**

| 文件                    | 改什么                                     |
| ----------------------- | ------------------------------------------ |
| `worker/src/html.ts`    | `escHtml` + `unescapeHtml` **两边都要改**   |
| `embed/src/render.ts`   | `escHtml` + `unescapeHtml` **两边都要改**   |
| `embed/src/render.test.ts` 第 35 行 | 那条"不认识的实体"断言里现在含 `&#x27;`，要更新 |

**第 35 行那条是这样的：**

```ts
it("leaves entities it does not produce untouched", () => {
  expect(unescapeHtml("&copy; &nbsp; &#x27;")).toBe("&copy; &nbsp; &#x27;");
  //                                       ↑
  //                      它把 &#x27; 当作"我不产生的实体"
});
```

**⭐ 这条测试是"反向声明"** —— 它断言"`&#x27;` 是我不该碰的东西"。
**你一旦让 `escHtml` 产生 `&#x27;`，这条测试的假设就过时了。**

**这正是一个有经验的开发者写测试时会考虑的事：**

> **不仅要测"我做了什么"，还要测"我不做什么"。**
> 因为后者定义了你的**边界** —— 边界一旦移动，这些测试就会提醒你。

| #   | 知识点                                                       | 为什么重要                                       |
| --- | ------------------------------------------------------------ | ------------------------------------------------ |
